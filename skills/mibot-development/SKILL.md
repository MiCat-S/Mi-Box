# MiBot 开发

以当前检出的 V2 源码和测试落实架构规范。仓库内维护本 Skill 的版本，安装副本用于发现和调用；两者不一致时，先核对当前仓库版本。本规范约束本次开发涉及的实现，不自动扩大为全仓迁移或部署。

## 定位工作范围

1. 读取目标仓库的 `AGENTS.md`、Git 状态、分支和相关差异。识别 Core 与插件的实际工作树；同级目录可能处于不同分支，不能仅凭目录名假定配套。
2. 找到 Core 的 `src/v2/sdk.ts`、`src/v2/runtime.ts`、`package.json` 和插件的 `<id>/v2.ts`。目录可能名为 `TeleBox-Core` / `TeleBox-Plugins` 或 `mibot` / `mibot-plugins`，不硬编码本机路径。
3. 确认行为的唯一所有者，再选择修改点。先读 [架构与依赖边界](references/architecture.md)；编写插件或命令时再读 [插件开发](references/plugin-development.md)；选取验证与交付步骤时读 [验证与交付](references/verification.md)。

## 必须保持的架构契约

- **运行入口**：Node.js 24 执行预编译的 `dist/v2/index.js`。Core 管理账号、宿主、调度、资源、发布和基础内置；业务扩展由 TPM 安装。
- **实现归属**：默认内置以 `runtime.ts` 的实际注册和归属测试为准；一个功能只有一处活动业务实现。Core 构建可独立完成，扩展之间通过 `ctx.services` 协作。
- **SDK 边界**：扩展使用 `telebox/sdk` 和 `PluginContext`，不导入 Core 内部路径或旧 `@utils/*`。账号客户端和 Host / Releases 管理实例由 Core 装配，按需注入管理内置。
- **声明与执行**：默认导出的工厂同步、无副作用；声明负责命令、过滤和帮助，资源在受管 `setup` 或处理器中获取。新结构化命令声明使用 `STRUCTURED_PLUGIN_API_VERSION`，与构件 ABI 分别管理。
- **资源所有权**：异步任务、HTTP 响应体、临时文件、子进程和调度都必须活在宿主可追踪的作用域中。取消后仍未完成的操作继续受管；超时不能算作清理成功。
- **状态与协议**：持久化使用插件命名空间内的受管存储；Telegram ID 保持精度。原生 RPC 使用正确的 TL 构造器，协议修复需覆盖真实 resolve / 序列化边界。
- **用户界面**：命令分发和帮助来自同一声明，使用当前前缀。消息过滤限定范围，授权检查决定权限，两者分别验证。

## 执行方式

先沿用户触发路径定位入口、路由、业务处理器、资源适配器和外部协议；为已证实的失败选择最小修复。SDK 缺能力时，先在 Core 定义并验证公共契约，再让插件消费。纯业务差异留在所属插件，避免复制宿主机制。

根据改动选择验证：纯逻辑测输入输出，协议问题测真实序列化，资源问题测取消和卸载，共享契约测跨仓兼容。报告实现结果、实际检查及其局限；代码推送、服务部署和真实 Telegram 验证是不同结果。

版本递增和提交推送遵循当前项目 `AGENTS.md` 与会话授权。Skill 本身不新增外部提交、账号操作、发布或部署授权。
