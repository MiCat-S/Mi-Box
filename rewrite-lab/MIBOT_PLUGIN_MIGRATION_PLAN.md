# MiBot 插件全量迁移实施方案

日期：2026-09-07。本文以本地源码核验结果为基线，是后续实施与验收规范，不表示所列工作已经完成。

## 1. 交付目标

采用现有 TypeScript + Node.js 24 + Teleproto + V2 SDK 架构，完成现有插件的功能、数据、权限、调度、媒体输出和安装更新迁移。生产运行提前编译的 JavaScript，由 systemd 管理。

每项完成必须同时满足：功能对照通过、旧数据可迁移、真实宿主可加载卸载、所需外部能力已验证、TPM 可以安装发布版本、资源验收通过。单纯存在 `v2.ts` 或 esbuild 构建成功不算完成。

默认体验遵循已确认的命令集合：

- 常用：agent、ai、gt、memory、ping、status、sysinfo、tpm、update。
- 系统：alias、autofix、bf、env、exec、help/h、loglevel、prefix、restart、sudo、version/ver。
- 其余功能通过 TPM 按需安装，help 从当前已激活命令注册表生成；卸载后同步消失，别名不重复计作插件。
- ai、gt 虽位于插件源码仓库，属于默认配套包；源码归属与默认安装策略分别管理。
- 生产常用的 da、dc、dme、ids、ip、nodeseek、rate、sum、yvlu 必须继续可用，但不因此成为所有新用户的默认安装项。

## 3. 先修正已有迁移的真实问题

此阶段先于批量增加新入口，避免将同一问题复制到更多插件。

1. 统一进程预算。宿主默认超时 30 秒、输出 1 MiB，而 audio_to_voice/rev 申请 180 秒、sticker_to_pic 申请 60 秒、qr 申请 2 MiB 输出。现有 SDK 只允许调用收紧限制，这些请求可能在进程启动前被拒绝。增加经过验证的宿主配置或明确的进程能力预算；禁止只在测试里替换 processes.run 后声称兼容。普通命令与媒体任务分别采用合适的期限。
2. 辅助程序探测只在 SPAWN_FAILED 且确认为缺失程序时尝试其他路径。超时、参数错误、输出超限不得反复换路径运行相同任务；暴露可定位的错误类别。
3. 恢复功能完整性。annualreport 的插件数、javdb 的定时销毁、rev 的格式实体等与旧实现逐项对照。替换实现要保留用户可观察语义；缺少的能力进入必做项，不能因删掉功能而算迁移成功。
4. 修复富文本与媒体边界。按 Telegram 解析后的文字长度分页；避免截断标签、实体和 UTF-16 代理对。消息长度与图片 caption 长度分别处理，长详情发送独立文字。验证 spoiler 实际传递到 Telegram 上传媒体类型。
5. 检查 JSON/SQLite 数据迁移。原来使用 SQLite 的功能改成 JSON 时必须有导入器，不能让旧配置悄悄变为默认值。保留未知字段与大整数精度。
6. 检查并发状态。按机器人串行化 music_bot 的搜索和回包匹配；按 chat/rule 串行化订阅更新；防止整点任务用旧快照覆盖刚发生的退订。
7. 核对 URL 边界。对于限制域名的 HTTP 请求，逐跳验证重定向；仅校验初始 URL 后自动 follow 不能证明实际目标仍在边界内。
8. 对 lu_bs 完成语法、时区、权限、任务冲突和订阅持久化验证，再进入发布队列。

## 4. 目标目录与职责

```text
Mi-Box/
  src/v2/                 宿主、SDK、默认内置、生命周期与传输
  scripts/                编译、TPM、服务安装、独立更新任务
  rewrite-lab/            盘点、功能矩阵、资源基线与验收记录
Mi-Box-Plugins/
  <id>/<id>.ts            迁移对照源码
  <id>/v2.ts              V2 工厂入口
  <id>/v2/               插件内部模块、模板与必要资源
  scripts/                插件级测试
```

当前 TPM 稀疏检出 `/<id>/v2.ts` 和 `/<id>/v2/`。因此运行所需数据、模板、字体、Python 脚本必须放入可获取的路径，并进入构建产物清单。禁止依赖开发机旁边的另一个仓库或未打包文件。

职责分配：

| 旧用法 | V2 迁移方法 | 验证点 |
| --- | --- | --- |
| Plugin 单例、构造时初始化 | 默认导出工厂，definePlugin；必要初始化放 setup | 两次加载没有共享脏状态 |
| cmdHandlers | commands，完整保留参数、别名和回复模式 | 与旧命令表逐条对照 |
| getGlobalClient/msg.client | context.telegram.withClient 或 invoke | 复用一个账号会话，不新增连接 |
| msg.edit/msg.reply | context.telegram.edit/reply，显式 parseMode | 文本、HTML、长消息均正确 |
| 直接监听 Telegram 更新 | listeners 注册到宿主 | 不重复监听，正确处理自己、他人及编辑消息 |
| setInterval/cron 单例 | jobs 或受 ResourceScope 管理的定时任务 | 卸载、重启、跨日后不重复执行 |
| 直接 JSON/SQLite 单例 | storage.json/sqlite 与版本化数据导入 | 原子提交、关闭释放、旧数据保留 |
| Axios/fetch 任意请求 | scoped HTTP，超时、大小、状态码与结构检查 | 失败不泄密，取消结束实际 I/O |
| exec/execFileSync | scoped processes，绝对路径、参数数组与预算 | 真正终止进程及其后代 |
| 共享 temp 文件 | files.withTemp，目录内执行并等待发送结束 | 上传前不删除，失败后能清理 |
| panelAdapter | settings，秘密字段由核心遮蔽 | TG 配置与面板使用同一份数据 |
| 跨插件 import 单例 | services.available/call | 未安装、卸载中、超时均有明确结果 |

SDK 暂缺能力时先补核心接口及测试，再迁移依赖插件。不得在插件里导入旧 @utils 或私自拿宿主内部对象绕过接口。

## 5. 每个插件具体怎么迁移

每项执行下面八步，状态顺序为：盘点 → 设计 → 实现 → 数据验证 → 宿主验证 → 外部联调 → 发布 → 验收。

1. **提取功能合同**：读取整个旧入口和引用文件，列出全部命令、参数、帮助、别名、监听条件、定时任务、权限、数据文件、外部服务、发送/编辑/删除行为。动态注册命令人工补齐。
2. **建立行为样例**：记录正常输入、无参数、回复文本、回复媒体、多行、长输出、权限拒绝、服务失败、取消时的预期结果。保留旧版有意义的输出信息和默认值。
3. **设计数据迁移**：标明旧路径、新路径、schemaVersion、字段映射、游标与任务 ID。先 dry-run，再写入副本，校验数量/内容后原子切换。源数据保留，重复执行应幂等。
4. **拆分实现**：v2.ts 负责注册与薄命令处理；只有确实复杂时才拆 parser/storage/provider/media 模块。轻量常量直接保留；重依赖按需导入，CPU 密集处理进入短期进程。
5. **实现完整功能**：按合同逐项实现，不用状态查询替代原来的执行功能。自动功能默认保持旧配置；新安装没有配置时保持关闭。
6. **真实宿主验证**：PluginHost 加载真实编译产物；外部 Telegram/HTTP 可用可控替身，宿主生命周期、存储、调度、进程不全部 mock。需要进程的功能在 Linux Node 24 中执行实际工具。
7. **外部验收**：用测试聊天、测试管理员和最小样本验证 Telegram 显示、按钮、媒体、定时、删除与回复目标。付费 API 使用最小请求；失败不能只返回成功占位文字。
8. **发布证据**：记录源码提交、产物 revision、测试记录、资源记录和回退版本。合入实际发布分支后，用全新目录从 TPM 安装验证。

每项台账至少包含：id、源码 hash、命令清单、功能清单、依赖、迁移器、实现状态、单元测试、宿主测试、真实联调、资源结果、发布提交、遗留问题。总状态由最弱的必需证据决定。

| xmsl | 迁移原有自动触发、目标和文本规则 | 过滤、频率、关闭与重启行为 |
| yt-dlp | 下载器参数、格式选择、进度、转码与发送迁移 | 播放列表、限额、下载中止、辅助进程 |
| zpr | 图源请求、选择、媒体输出与配置迁移 | 图源失效、媒体格式、数量与大小 |

## 7. 数据与重启语义

配置与运行状态分开存储。配置保留用户意图，运行状态保存游标、任务 ID、下一次运行时间、最后成功结果。秘密字段不出现在日志、普通面板返回、测试快照或 Git 中。

迁移器执行顺序：检查版本与格式 → 读取源数据 → 写入临时副本 → 校验字段和数量 → 原子切换 → 记录迁移版本。失败保留源数据并明确报错，不能返回空对象冒充成功。

定时发送属于外部副作用，通常无法保证跨崩溃严格 exactly-once。为每次触发生成稳定任务键，记录 prepared/sent 状态与返回消息 ID；重启时核查不确定任务，优先避免重复发送，同时允许可见的人工重试。删除与撤销类任务保留到期记录并幂等重试。

避免存整条 Telegram Message 或大媒体 Buffer 作为长期状态。保留 chatId/messageId/必要实体引用，ID 使用字符串；需要时重新读取并处理 fileReference 过期。

## 8. 低资源实施与衡量

“最低资源”采用同机、同功能、同负载比较得出，不承诺不可证明的绝对最低值。功能集保持完整，默认安装仍精简，未安装插件不加载。

- 一个主账号连接；插件卸载后释放监听、任务、网络、数据库与进程。
- 主体预编译，安装编译器短时运行；按需加载图像/分词/HTML 等依赖。
- 普通业务有界队列，重媒体初始并发 1；缓存限制条目、字节和 TTL，过期有清理途径。
- 媒体优先流式落盘，限制下载字节、帧数、像素、时长和并发；输入与输出峰值一起统计。
- 频繁到期任务采用合并调度，避免每条消息长期持有庞大对象或重复扫描全历史。
- 进程限额与 systemd 控制组共同约束；超限必须给出可见失败，不能制造频繁重启。

保留原计划验收要求：同机顺序 A/B 至少 5 次；稳定空闲总 PSS 降低至少 25%，代表负载峰值不增加，CPU 时间不超过旧基线 105%，吞吐不低于 95%；本地预热 p95 不超过基线 110%，允许 10ms 测量容差；重型冷启动额外开销不超过 2 秒，远端服务等待单列。

比较业务并发 2/4/8、重型并发 1/2、保温 0/60/120/300 秒；保温机制确实需要时再实现。满足全部约束后选 PSS 最低组合，差异不足 5% 选 CPU 更低者。总量包含 Python、FFmpeg、渲染进程及日志增量。

验证 50 次加载/卸载后资源无泄漏，24 小时代表性负载后无持续增长。若旧基线无法运行，记录无法比较的原因，使用绝对资源报告，但不能宣称达到 25% 改善。

测试分层：纯解析和规则测试；真实 PluginHost 加载/卸载与持久化测试；Linux 真实辅助程序测试；Telegram 测试聊天联调；资源和升级回滚测试。每层报告覆盖范围。仅 mock 成功返回的测试不足以证明媒体转换、权限或真实 RPC 构造正确。

特别核验：指令重命名和别名冲突、所有者判断、编辑消息重入、按钮 Layer 229 类型、parseMode、字幕长度、进程选项合法性、线程/topic 回复目标、定时任务时区。

### 发布顺序

1. 每插件或独立小批提交，记录差异与证据；Core SDK 改动独立提交。
2. 依赖新版 SDK 时先发布 Core，并记录最小兼容版本，再发布相应插件；旧宿主给出可理解的升级提示。
3. 将通过门槛的插件合入 Mi-Box-Plugins/main。验证 main 的具体 SHA，再通过 TPM search/install/update 安装。
4. 测试一次默认安装：只出现默认命令；安装扩展后 help 增加；卸载后消失；重启与 .update 后安装集合保持。
5. 更新控制器由独立 systemd 任务执行；持久化原 chat/message/task ID，成功或失败写入结果，服务恢复后在 Telegram 更新原通知或发送可关联结果。
6. 验证“任务无法启动”“构建失败”“重启失败”“结果通知失败”分别可定位。不能把已提交请求当作已完成更新。
7. 在备份后的测试部署验证，再升级日常生产集合，观察后扩大到其余兼容组合。

### 回滚

保留上一 Core 产物、插件 revision、激活清单、服务定义与升级前数据快照。先停止目标实例，再恢复兼容代码和激活清单，保留升级后新增数据；schema 不兼容时运行反向迁移或恢复经确认的数据副本。验证只有一个账号实例运行，Telegram 命令与定时任务恢复。

## 10. 执行批次与并行方式

1. **基线与补修**：更新台账、修正宿主预算、发布分支衔接、已有入口功能回退与数据问题。退出条件：已实现入口真实宿主验证通过，历史范围全部登记。
2. **SDK 与状态能力**：补齐命令执行服务、可恢复任务、必要 Telegram 实体/权限与资源边界。退出条件：下游无需导入旧运行时。
3. **消息与管理**：his/search/save、管理员与删除类，配合测试群验证权限和目标。
4. **定时与监听**：acron/sendat、自动删除/复读、keyword/shift/pmcaptcha、监控；验证跨重启状态机。
5. **媒体与生成**：转换、贴纸、词云、模板、音乐、TTS、图像 API；完成真实工具和视觉验收。
6. **外部服务与系统**：搜索、图源、面板 API、SSH、NTP、WARP；每个独立依赖记录可用性与失败结果。
7. **全量收口**：历史入口归属、默认安装、TPM、更新反馈、回滚、50 次重载和 24 小时资源验收。

并行任务按依赖和文件所有权划分为消息管理、调度状态、媒体渲染、网络服务四组。每个子任务只写指定插件及对应测试；Core、发布索引、台账和集成由主任务负责。每次交付包含文件、合同差异、实际运行命令和失败项。不能将子任务“完成”直接记为总体验收通过。

先完成宿主能力，再启动依赖它的批次；独立插件可并行。每批大小由测试和审查能力决定，不以新增 v2.ts 数量作为速度指标。工期在完成合同盘点后按实际复杂度估算，不用剩余插件数乘固定时间。

## 11. 最终完成判定
